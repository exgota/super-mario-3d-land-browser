# Passive guest write observation

`runtime/port/GuestWriteObservation.{h,cpp}` provides optional diagnostic JSON Lines output for naturally invoked static-backend Write8, Write16 and Write32 callbacks. The selected root word address and slot offset come from runtime configuration. The source contains no selected game address, layout or captured data. This feature does not establish World 1-1 entry, Section 7 state semantics or a milestone result.

## Configuration and build

The `azahar_static_execution` frontend accepts these environment variables:

| Variable | Required value |
| --- | --- |
| `ROOT_PORT_GUEST_WRITE_PATH` | An absent output file in an existing directory. Creation is exclusive, including refusal of an existing symlink. |
| `ROOT_PORT_GUEST_WRITE_ROOT` | An aligned 32-bit guest virtual address whose complete four-byte word fits in the address space. |
| `ROOT_PORT_GUEST_WRITE_SLOT_OFFSET` | An unsigned 32-bit offset added to the observed nonzero root value with checked wide arithmetic. |
| `ROOT_PORT_GUEST_WRITE_EVENT_LIMIT` | Optional positive limit, default 4096, maximum 100000 relevant events. |
| `ROOT_PORT_GUEST_WRITE_BYTE_LIMIT` | Optional output limit including the footer, default 16777216 bytes, allowed range 8192 through 67108864 bytes. |

Numbers use unsigned decimal or a `0x` hexadecimal prefix. Empty, signed, whitespace-padded, trailing or out-of-range values are refused. All variables unset returns a null observer. A partial configuration is refused before headless capture. The disabled backend path performs the existing memory write with no observation RAM reads or register snapshots.

Apply `azahar_guest_write_observation.patch` as an additional source-only patch after the accepted provider patch sequence, including `azahar_static_execution.patch` and `azahar_state_observation.patch`. It adds the new source to both static-backend targets because both link `StaticArmBackend.cpp`. It changes no provider behavior or accepted patch. The compiled-module frontend retains its existing default null observer; only the native-library frontend wires this environment configuration.

Both `StaticArmBackend` constructors append an optional shared observer argument after the unchanged memory trace argument. `GuestMemoryTrace.{h,cpp}` and its existing Write32 call remain unchanged. Root built an isolated native-library frontend and checked disabled/enabled replay, read-unavailable behavior, bounded failure and full input/GPU/pixel/audio/tick preservation. The compiled-module frontend is not built by this evidence. Native build and replay commands, final source hashes and limits are recorded in `project/guest_write_observation_evidence.md`.

## Sampling and event fields

`ChargeBlock` copies the sixteen general registers, CPSR, all sixty-four raw floating-register words, FPSCR, FPEXC, TLS, exclusive metadata and timing counters before invoking the existing scheduling method. This is `instruction.charge_entry_context`. The instruction address, span, per-backend generation and observer-assigned context identity remain separate from architectural R15. Admission by the existing scheduler marks the snapshot valid. Run entry, supervisor handling, SetPC and LoadContext invalidate stale snapshots.

Every observed write callback reads the actual `MemorySystem::GetCurrentPageTable()` used by the existing write. Passive reads check every requested byte for `PageType::Memory` and a nonnull entry in that table's existing pointer array before dereferencing any byte. They read no service, MMIO, watchpoint or rasterizer path and invoke no guest code. Byte assembly is explicit little endian. Invalid reads report a reason with null bytes and value. Wrapped destination extents and overflowing slot extents remain invalid rather than being folded into a readable range.

An event is relevant when its one-, two- or four-byte virtual destination overlaps the selected root word or the current slot derived from the pre-write root. Partial overlap and same-value writes remain relevant. A wrapping destination is checked against both virtual ends for relevance, but cannot provide a valid destination read. Null or unreadable roots prevent deriving a slot; footer counters expose unavailable root/slot selection even for callbacks without an emitted event. Physical aliases and writes outside these callbacks are outside the selection contract.

For relevant callbacks, `before` contains the root word, derived slot and a repeated root read. `callback_entry_context` is sampled at callback entry. The existing actual memory write is invoked exactly once. `after_store_context` is copied immediately when that write returns or throws. `after` then reads the root and its current slot again. `previous_slot_after` separately reads the original slot address, so replacing the root cannot confuse old-slot evidence with the new current slot. Destination and four-byte raw instruction prefixes are read at callback entry and after the store. Thumb state comes from the saved CPSR; the prefix does not decode Thumb instruction length.

The event reports the actual table's equality across callback entry and after store, its equality to the backend's separately stored table at charge/callback/post phases, and stable byte-location mappings for root, old slot and destination. Each phase's `coherent` flag requires a valid slot and an unchanged, mapped root recheck. `coherent_memory_join` additionally requires both phases, stable mappings, the same actual table, matching backend tables and a returned write. These are consecutive passive samples, not an atomic memory transaction or a freeze of other host activity. The observer performs no locking or guest mutation to manufacture coherence.

`write_returned` reports whether the existing memory write returned. `destination_matches_supplied_bytes` is null if the post-destination read is unavailable. `committed_bytes_observed` requires a returned write, valid pre/post destination reads at the same byte locations and equality of the post bytes to the supplied value. `same_value_store_observed` adds equality of the pre bytes to that value. These fields describe observed destination bytes; they do not independently establish successful exclusive-store semantics or a source-level publication. Full writer evidence additionally needs the coherent root/slot join, instruction provenance and original-code checks.

`instruction.precise_pre_instruction_context` requires an admitted one-instruction span, a callback associated with the same backend context and timing generation, and stable actual/backend table association. Wider spans retain bounded-call entry metadata and no precise PC candidate. `precise_pc_candidate` additionally requires readable raw prefix bytes. The raw `timing_address` and saved `instruction_set` remain intact. Only a saved Thumb state permits clearing its address tag bit for the RAM read and candidate; a misaligned ARM address is invalid and is never masked into another word. It remains a candidate until root validates the timing address, original executable words and actual callback correspondence. The per-charge `callback_ordinal` counts every naturally observed callback, including unselected callbacks, and distinguishes multiple micro-stores from one instruction. Callback-entry registers may already reflect translated pre/post-index writeback, so source operands must use the distinct charge-entry snapshot. `after_store_context` is not full architectural post-instruction completion; every event explicitly reports `architectural_instruction_completion:false`.

## Bounds, completion and limits

The stream begins with configuration, emits ordered relevant event rows, and ends with an explicit footer. Global callback sequence and event sequence retain selection/order information; context identity, CPU id and timing generation retain the callback's source context. The event cap and byte cap are independent. Two KiB of the byte cap are reserved for the footer. Exceeding either cap throws after the current actual write, stops successful observation and records an incomplete footer if output remains writable. There is no silent successful truncation. An existing write exception remains the original exception; an attempted failure event cannot replace it.

`footer.complete:true` requires successful headless capture, no lost records, no failed memory writes and no output/bound error. It describes transport completeness. Each event's read validity and coherence still determine whether it supplies usable writer evidence. Footer counters distinguish callbacks with unavailable selection, emitted events with unavailable evidence, imprecise spans, failed writes and omitted events. Failed capture gets an incomplete footer; destruction without explicit finalization also attempts an incomplete footer. An output failure can prevent even a footer, which leaves no complete stream. The enabled frontend cannot return successful capture with an incomplete observation. Abrupt process termination has no complete-footer guarantee.

Three actual 360-presentation native replays preserve the original movie outputs with zero CPU fallback: disabled, enabled for a configured current-root slot, and enabled for an unreadable root. The enabled stream has two naturally invoked writes; one coherent current-root slot store matches its original instruction, charge-entry source/effective-address operands and read-after destination. Observed host times are 56.2846781, 70.3667549 and 62.2322830 seconds in this local run, not a performance guarantee. Ten real configuration/output refusals stop before capture; event and byte cap controls fail naturally with incomplete footers. Existing fixture bytes and link targets preserve. Runtime checks used recorded passive witnesses and unchanged full movie comparison. Unexercised partial-overlap, same-value, wrapped-destination, readable cross-page, exclusive-store and page-remapping branches retain their explicit validity contracts but are not claimed tested by these captures. A complete emitted stream does not establish complete writer coverage: unavailable relevant root/slot reads and HLE or direct-memory writes outside the callbacks remain gaps. No event establishes a class, controlled player, object ancestry, lifetime, update phase or completed gameplay state. Original instruction validation and coherent natural receiver evidence remain external requirements.
