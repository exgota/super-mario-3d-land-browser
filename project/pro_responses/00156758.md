## What the remaining 31 bytes imply

The reported stack count is exactly consistent with the existing stack-location differences:

| Object or adjustment | Previous best layout | Target |
|---|---|---|
| Local frame | 0x1C | 0x2C |
| Holder-name SafeString | sp+0x00 | sp+0x18 |
| Enable argument | sp+0x10 | sp+0x0C |
| Nerve argument | sp+0x14 | sp+0x20 |
| Child-name SafeString | sp+0x08 | sp+0x10 |

That accounts for 3 bytes in the frame adjustments, 5 in holder-name setup, and 3 each in enable, nerve, and child-name accesses: 17 total. The holder-name setup contributes five rather than three because mov r1,sp must become add r1,sp,#0x18. This decomposition follows the supplied diff; it is not a new compiler measurement.

The required maximum sequence remains:

```asm
001568DC ldr r1, [r4, #0x64]
001568E0 ldr r0, [r6, #0x60]
001568E4 cmp r0, r1
001568E8 strgt r0, [r4, #0x64]
```

Six differing bytes are consistent with exchanging those two load instructions while leaving their destination registers and the comparison/store unchanged. All three candidates therefore use two separate, ordered volatile reads, not merely a volatile maximum read followed by an ordinary child read. The purpose is to constrain observable access ordering; it does not prescribe register allocation.

The constructor target is:

```asm

0015687C mov r2, r7
00156880 bl #0x277da0
```

This time, the constructor alternatives change argument representation or argument category, rather than only rearranging scalar parameters. These remain scheduling hypotheses, not language-level guarantees.

## 1. Typed holder-name member, text-first child construction, name/count argument record

Why I rank this first: it retains an ordinary outer new BeatBlock(...), but removes the old materializeName(slot, lookup(...)) helper shape.

The important expression is:

```cpp
( childText = al::getLinksActorObjectName( info, childIndex ),
*::new ( static_cast<void*>( frame.childName.bytes ) )
sead::SafeString( childText ) )
```

The lookup is the left operand of the comma expression. Placement construction is on the right. This is intended to stop the front end from creating a name-slot pointer as an argument that then remains live across the lookup. Crucially, the whole expression remains inside the outer allocation's initializer, preserving the target's opportunity to skip the lookup on allocation failure.

The holder name is now a real SafeString member, constructed after fn_00277de0, rather than a reference returned by a placement helper. The pinned SafeString has an inline empty destructor, so no destructor side effect needs to be introduced. Whether ARMCC eliminates all associated cleanup and avoids promoting a frame address remains a testable uncertainty.

The group receives a by-value {name,count} record. Its intended effect is scalar replacement into name-first argument components. An actual stack-resident argument record is a failure, not an intended extra local.

## 2. Split enable/name storage and an array-reference group constructor

This is the alternative when ARMCC still treats Form 1 as one escaping aggregate and promotes its address.

The intended local allocation is:

```
sp+0x00: BeatBlockEnableLocals, size 0x10
enableArgument at +0x0C

sp+0x10: BeatBlockNameLocals, size 0x1C
childName at +0x00 -> sp+0x10
holderName at +0x08 -> sp+0x18
nerveArgument at +0x10 -> sp+0x20
```

The two objects total 0x2C, but their order on the stack is not guaranteed. This form exchanges the monolithic record's fixed internal relationships for a chance to avoid a persistent common frame-base register.

The group constructor accepts a reference to the literal's character array, rather than a const char* scalar argument or a count-only constructor. It still calls the same out-of-line LiveActorGroup(const char*,int) and introduces no named static string. The intended perturbation is that pointer decay originates within the instantiated inline constructor. The pinned base constructor remains declared in the header and defined separately.

## 3. POD frame with explicit child allocation and post-lookup placement construction

This is the more invasive lifetime experiment.

It retains raw, offset-checked storage but removes the nested allocation/construction expression for the child. The sequence is explicit:

```
allocate child
test allocation result
look up text
construct SafeString in its stack slot
construct BeatBlock in the allocated child storage
initialize child
update maximum
register child
```

The intended benefit is that the SafeString-slot pointer need not exist across either the allocator call or the name-lookup call. The only child pointer that must survive those operations is the one intended for r6.

I rank it below the ordinary-new forms because explicit operator new and placement construction can perturb the already-correct null path, register coalescing, and constructor-result handling. It must reproduce the original allocation region, not merely equivalent behavior.

The group argument record is now {count,name}, reversing the aggregate component layout from Form 1. This tests a different component-to-base-argument remapping while keeping the base ABI, group extent, literal contents, and virtual interface unchanged.

## What remains deliberately unchanged

The actor hierarchy, member offsets, and virtual slots are not being used as tuning knobs. The pinned LiveActor definition has the required interface inheritance order and 0x60 size assertion, while MapObjActor adds no fields. The group still has its existing virtual registerActor and out-of-line base constructor.

In particular, maximumBeatIndex remains a nonvolatile member, and its pre-loop zero initialization remains nonvolatile. That preserves the opportunity for:

```asm
add r2, r4, #0x60
mov r5, #0
stm r2, {r0, r6}
```

The volatile qualification applies only to the loop accesses. All three retain the separate nerve calls, ordinary group allocation, exact Shift-JIS bytes, and declaration-only external providers. The target's existing register roles remain the objective: r4=this, r9=&info, r8=SafeString address point, r7=-1/childCount, r6=zero/block, and r5=childIndex.

## Confidence and what to inspect if all three miss

These are subjective whole-interval matching estimates, not measured probabilities:

| Rank | Exact-match confidence | Principal uncertainty |
|---|---|---|
| 1 | About 8% | Whether text-first construction removes the extra address lifetime without aggregate promotion or new argument storage |
| 2 | About 5% | Whether ARMCC allocates the two local records in the intended order |
| 3 | About 4% | Whether explicit allocation reproduces the already-correct child allocation/control-flow sequence |

First inspect the first definition of any new r10 or r11. An address derived from sp points toward stack-address promotion; a group-name or argument-record value surviving allocation points toward the constructor experiment. Do not attribute both to "padding." The prior 0x30 frame is consistent with a 0x2C object plus different alignment after an extra register save, so removing that save may matter more than shrinking the declared object. The published result establishes the extra save and larger frame, but not which value occupied r10.

Then separate frame extent from slot placement. Require the seven-register push, sub sp,sp,#0x2C, both matching epilogues, and all four accessed object positions. A correct decrement with wrong member addresses is not a stack win. Conversely, uniformly shifted offsets suggest a record-base placement problem rather than incorrect internal member layout.

For the six maximum bytes, inspect loads before changing comparisons. The objective is maximum into r1 first, child index into r0 second, then unchanged cmp r0,r1; strgt r0,[r4,#0x64]. If the larger forms regress, applying only the child-read qualification to the measured 524/31 source is the clean diagnostic: 524/25 is the predicted result if the six-byte diagnosis is correct and nothing else moves. That is a prediction, not a result.

For the constructor's eight bytes, check the PC-relative displacement as well as instruction order. With the correct pool position, the name-address instruction at 0x00156878 needs #0xCC; the same address calculation one instruction later would need #0xC8. Merely seeing an ADD and a MOV is insufficient. If all three argument forms normalize to the same reversed schedule, preserve whichever stack and maximum sub-forms improved and stop treating scalar parameter spelling as evidence of a new experiment.

Finally, retain the 468-byte executable / 56-byte pool boundary at 0x0015692C, including the SafeString address point 0x003D9C3C and group address point 0x003D66E8. A scratch exact match would still leave the recorded BeatBlock-constructor ownership and group-table ownership prerequisites unresolved; none of these forms supplies a map or provider-ownership workaround.
