### B. Loop-only volatile access: suppress the unconditional-store transformation

This is the strongest individual change.

The packet's best form turns the source conditional into:

```asm
ldr r1, [r6, #0x60]
ldr r0, [r4, #0x64]
cmp r0, r1
movle r0, r1
str r0, [r4, #0x64]
```

The target is:

```asm

001568E0 ldr r0, [r6, #0x60]
001568E4 cmp r0, r1
001568E8 strgt r0, [r4, #0x64]
```

Thus the necessary correction is not just reversing a comparison. The compiler must retain the conditional memory write instead of computing a selected value and writing on both paths.

In the candidate, the false path contains no volatile store. Introducing an unconditional volatile store would add an observable access, so this gives the optimizer a reason not to perform the particular transformation seen in the packet.

The desired allocation is oldMaximum → r1, childBeat → r0, followed by cmp r0,r1; strgt r0,[r4,#0x64]. Declaring the old-value read first and putting the child value on the left of > is intended to encourage that ordering. It does not guarantee those registers or the scheduling of the nonvolatile child load.

Keeping the member declaration nonvolatile is equally important. The earlier initialization must remain eligible for the target's combined store:

```asm

mov r5, #0
stm r2, {r0, r6}
```

That writes the newly allocated group pointer and zero maximum together. A globally volatile maximum would also constrain this earlier operation. The access qualification in this proposal is confined to the loop.
