## 3. Compiler behavior targeted by the changes

### A. Correct the accumulator's two distinct live values

This is the most certain correction. The target performs:

```asm
001FA0C8: sub r2, r7, r2
001FA0CC: ldr r7, [r0, #0xe8]
001FA0D0: add r8, r8, r2
...
001FA0DC: mul r7, r7, r8
...
001FA0EC: sub r2, r2, r7, asr #7
001FA0F0: str r2, [sb, #0xcc]
```

Thus r2 remains the terminal-stage delta, while r8 becomes old accumulator + delta. The final subtraction uses r2, not r8.

The necessary source dependency graph is:

```cpp
int delta = terminalValue - scaledDifference;
int sum = oldAccumulator + delta;
int nextAccumulator = delta - ((coefficient * sum) >> 7);
```

Form3 instead subtracts the correction from sum. For a non-overflowing example with oldAccumulator = 128, delta = 256, and coefficient = 64, the target produces 64, while Form3 produces 192.

Keeping result and accumulated separate also targets the observed allocation: result can remain in r2; the short-lived sum can occupy r8 and die after the multiply. This removes a wrong dependency rather than merely changing variable spelling.

### B. Make only the local pointer slots volatile

The target reads the local pointer table at both ends of every sample iteration:

```asm
001F9FB0: add r2, sp, #0x10
...
001F9FB8: ldr r2, [r2, sl, lsl #2] ; input pointer
...
001FA100: add r7, sp, #0x10
001FA104: ldr r7, [r7, sl, lsl #2] ; output pointer
```

It also copies all four incoming pointer words before entering the channel loop. Form3 instead caches the selected sample pointer and spills the channel value, contributing to its different register allocation and 0x2C frame.

The proposed declaration is deliberately `int* volatile sampleBuffers[4];` — not `volatile int* sampleBuffers[4]`.

The intended ARMCC effects are:

- Preserve the four local pointer-slot initializations.
- Retain separate pointer-slot reads for input and output.
- End the input pointer's useful lifetime after the input load instead of carrying it through the feedback stages.
- Make channel useful twice per sample, increasing the incentive to retain it in a register such as target sl.

This is a code-generation hypothesis, not evidence that the original declaration contained volatile. It also does not force a particular register number, stack offset, or instruction schedule. Volatile-access details are implementation-defined; the compiler-specific result still needs observation. (Source cited: EEL.)

This is materially different from the packet's already-tried unsigned-storage form, which produced identical bytes to Form3.

### C. Snapshot the primary coefficient before either buffer write

The target loads state + 0xDC before writing either the primary or secondary buffer:

```asm
001F9FBC: ldr fp, [r0, #0xdc]
...
001F9FC8: str r2, [r7, r3, lsl #2]
...
001F9FD4: mul fp, r8, fp
...
001F9FDC: str r2, [lr, ip, lsl #2]
```

Form3's coefficient expression occurs after those writes.

The explicit local `int primaryCoefficient = state->primaryCoefficient;` preserves the earlier read even when considering potential aliasing between an int buffer and an int state member. The multiply is separate and can still be scheduled later, as in the target.

This also gives the allocator the desired lifetime: fp initially contains the coefficient, then the primary contribution, which the target spills to [sp, #4] before the feedback work. I would not add restrict or cache all coefficients: that would introduce unsupported alias assumptions and change other load-placement opportunities.

### D. Preserve the target's register-pressure structure

| Register | Target role |
|---|---|
| r0 | State pointer |
| r1 | Sample counter |
| r3 | Primary index |
| ip / r12 | Secondary index |
| r4, r5 | First and second feedback indices |
| r6 | Terminal index |
| sb / r9 | State plus 4 * channel |
| sl / r10 | Channel counter |

| Offset from adjusted sp | Value |
|---|---|
| 0x00 | Saved first-feedback value |
| 0x04 | Primary contribution |
| 0x08 | Secondary-buffer pointer |
| 0x0C | Primary-buffer pointer |
| 0x10–0x1C | Four copied sample-buffer pointers |
| 0x20 | State plus 8 * channel |

That accounts for all nine words of the 0x24 frame. The target separately pushes nine registers.

The proposal tries to remove Form3's cached sample-pointer lifetime and keep the channel counter useful in the inner loop. It does not attempt to encode this table with a fabricated stack-layout struct. Stack-slot order remains an allocator decision.

The initialization order also places the adjacent feedback-index loads together, offering the opportunity for the target's `ldrd r4, r5, [r0, #0xb0]`. That is an opportunity, not a guarantee: declaration order alone cannot prescribe LDRD or the destination pair.

The state layout is deliberately unchanged. Its pointer banks naturally support the target's two address expressions, state + 4 * channel and state + 8 * channel; reorganizing it into an invented per-channel record would fight the observed addressing.

### E. Retain the asymmetric branch and coefficient lifetimes

The target does not use one uniform sign-handling pattern throughout. The first two feedback stages have separate negative/nonnegative paths with coefficient loads in those paths. The terminal stage retains one coefficient across the terminal-buffer store and uses predication; the subsequent sign decision consumes flags from ADDS.

The candidate therefore keeps the `if (firstFeedbackValue < 0) ... else ...` form with coefficient accesses inside the expressions, but uses a retained terminalCoefficient and destructive arithmetic on terminalContribution.

In particular, `difference += terminalContribution; terminalBuffer[terminalIndex] = difference; if (difference < 0) ...` is intended to make the target's ADDS, intervening store, and PL-predicated path available. Whether ARMCC chooses that form rather than Form3's different predication is one of the principal remaining uncertainties.

The five index increments remain at the end of the source loop. Since they are independent of the accumulator multiply once their final buffer accesses are complete, this leaves the scheduler room to interleave them with that multiply, as the target does at 0x001FA0D4–0x001FA0E8.

### F. Preserve signed loop tests, unsigned wrapping, and an empty literal pool

The sample and channel counters remain signed int, matching the target's BLT loop tests. The five ring indices and lengths remain unsigned, matching the final HI/LS conditional stores. Indices are reloaded for each channel and committed only after both channels; this is not a per-sample modulo operation.

The required literal-pool order is empty. The four copied pointers are runtime stack contents, not pool entries. The target ends with its return at 0x001FA180, immediately before the 0x001FA184 boundary. There is no trailing pool to reproduce or reorder. Consequently, Form3's eight-byte size deficit must not be "fixed" with padding or invented constants.

The candidate introduces no helper functions, static tables, external data references, or 64-bit arithmetic. Keep the packet's complete flag sequence—including duplicate flags and frozen preinclude—unchanged.
