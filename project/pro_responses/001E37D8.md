## 1. Returning factory-and-append helpers

Compiler behavior targeted: this is my first choice because it retains typed new, but changes the optimization boundary around the troublesome results.

For Movement, CalcAnim, Layout, and Functor, the helper constructs, appends, increments, then returns the pointer. The loop-common executor receives that result afterward. Combined actor and Execute deliberately keep direct assignments to executor before appending.

The hypothesis is that this gives ARMCC a distinct short-lived factory result to retain through the append, instead of immediately coalescing it with the loop-common value. That could produce the required r1 counter updates and the shared late layout/functor move. It does not bind an inline function's return to r0; the desired register allocation remains a prediction.

Compiler behavior targeted: this changes two substantive things: constructor lowering uses explicit guarded calls, and the important joins are represented directly in the source.

Movement and CalcAnim meet at one actor append. Layout and Functor meet at one executor = pending assignment. Combined actor and Execute assign executor before their category append.

The first actor pair keeps pending live through the counter update; obtaining the exact target still requires ARMCC to schedule its copy to r6 earlier. The layout/functor join, however, is explicit rather than dependent solely on merging independently written tails.

The address-derived constructor imports return pointers deliberately. ## Confidence and what to inspect if all three miss

| New form | Exact-byte confidence | Main uncertainty |
|---|---|---|
| 1 — Returning factory | Low-to-moderate; strongest first trial | Whether the inlining boundary changes result coalescing enough to preserve the target's append lifetimes. |
| 2 — Collection view | Low | Whether reference/view scalar replacement disappears completely while still changing allocation and scheduling. |
| 3 — Explicit joins | Low | Whether ARMCC preserves the intended joins, null-result lowering, and instruction schedule. |

These are comparative judgments, not calibrated probabilities. The first-pass register swap is the weakest prediction across the three forms.

Inspect the first differing logical block, not just the total byte score.

First-pass allocation. Check 0x001E37F8 and 0x001E380C: the target starts the count in r7 and forms the entry address in r6. Also compare the nearby zeroing, comparison, and first-array-result store schedule. If a candidate fixes the entire second pass but still swaps these registers, preserve that second pass and isolate the counting pass next.

Append lifetimes and the extra move. For layout, the required sequence is:

```asm
add r1, r4, #0x24
ldm r1, {r1, r2}
str r0, [r2, r1, lsl #2]
ldr r1, [r4, #0x24]
add r1, r1, #1
str r1, [r4, #0x24]
b shared_move

; shared with functor:
shared_move:
mov r6, r0
```

Look for an early mov r6,r0 followed by reuse of r0 for the counter, or duplicated moves on the layout and functor paths. Conversely, do not "fix" combined actor and Execute to use this shape: their target uses r6 for the stored pointer and ldrd r0,r1 for the collection fields. The first actor pair also has its own schedule, including an earlier copy to r6.

Code length before pool differences. The last return must be at 0x001E3B08; the pool must start at 0x001E3B0C. That is 820 bytes of instructions plus 88 bytes of literals. A single extra instruction shifts later branches, PC-relative string references, and the pool, producing many byte differences without many independent source errors. The required pool is:

| Address | Literal | Padded extent |
|---|---|---|
| 0x001E3B0C | ActorMovement | 16 |
| 0x001E3B1C | ActorCalcAnim | 16 |
| 0x001E3B2C | ActorMovementCalcAnim | 24 |
| 0x001E3B44 | LayoutUpdate | 16 |
| 0x001E3B54 | Execute | 8 |
| 0x001E3B5C | Functor | 8 |

If a candidate becomes four bytes short, inspect whether it has incorrectly merged an actor path into the layout/functor tail or removed a target conditional-zero instruction. Do not compensate by adding a NOP.

Reject structural regressions before tuning scheduling. Extra helper calls, view-object spills, array clearing, used-count resets, changed constructor targets, or caching _C across the construction loop are larger failures than the remaining register choice. If instructions and length match but calls differ, inspect constructor bindings before changing source. If all three produce the same append schedule, the proposed helper boundaries have been optimized away; renaming locals is not a meaningful next experiment.

Finally, do not initialize sl merely to "repair" the target's mov r1,sl before array allocation. The ARM C++ ABI permits a meaningless second argument to library nothrow new/new[], which those functions must not inspect. The source should continue to let the packet's unchanged allocation lowering produce that setup. (Source cited: github.com.)
