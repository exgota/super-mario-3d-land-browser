### Compiler behavior targeted

The key hypothesis is that a separately optimized, subsequently inlined whole iteration gives ARMCC a better opportunity to reuse the dying slot and comparison temporaries.

On the nonmatch path, element dies at the comparison, and the helper immediately produces the next bound. That is the desired transition:

```
cmp r4, r1
ldrne r2, [r3, #4] ; slot address no longer needed
bne 0x252BA0
```

On the match path, the loaded actor is dead before lastIndex is introduced. That makes the target's reuse of r4 natural. The buffer is needed until the last-element load but not afterward, allowing ip to hold that loaded replacement:

```
ldr r4, [r3, #4]
cmp r4, r0
ble 0x252B94
sub r4, r4, #1
ldr ip, [ip, r4, lsl #2]
str ip, [r2]
```

Finally, return --mSize supplies one result to the loop latch. It keeps the post-replacement count read distinct from lastIndex, while making a second reload after the decrement store unnecessary in the source data flow. These are precisely the target's lifetime transitions.

What this does not guarantee: an inline helper does not impose its standalone calling convention on the final function. I am not expecting an ABI return register to "force" the bound into r2. This is an optimization-shape and register-coalescing hypothesis.

Likewise, representation-copy reads are not memory barriers. A nonmatch path contains no intervening write that semantically requires another count load. Retaining that redundant-looking load still depends on ARMCC's optimization shape, as the earlier response noted.

Main risk: ARMCC flattens this back to old form 2, producing identical bytes, or its helper-level optimization removes the match-bound check. A surviving call, copy routine, or stack temporary is a structural rejection.

### Compiler behavior targeted

The append no longer passes through a returned one-pointer aggregate followed by a representation-copy store. Instead, its final operation is a typed assignment to an element reference.

My hypothesis is that this gives address selection a cleaner opportunity to retain buffer base plus byte offset until the final store, rather than finishing a complete element pointer for a copy operation. The desired append is:

```
00252BD8: add r0, ip, #1
00252BDC: str r0, [r5, #4]
00252BE0: ldr r3, [r5, #8]
00252BE4: mvn r2, #3
00252BE8: add r0, r2, r0, lsl #2
00252BEC: str r1, [r3, r0]
```

Notice the relationship between scheduling and allocation here. Once the new count has been stored at 0x252BDC, its original value no longer has to remain available for a later count store. Its register can be overwritten by the byte offset at 0x252BE8. In the historical variant-5 comparison, the count store was delayed until after offset formation, and count and offset occupied different registers. That is a concrete reason to examine these two differences together, rather than treating them as unrelated register substitutions.

I deliberately retain mSize - 1 rather than introducing a byte-pointer cast, a manually scaled offset, or a saved old index. Those changes would add another variable to the address-selection experiment.

Main risk: a reference return still denotes an address; it does not guarantee an indexed final store. Nor does ++mSize; return mBuffer[...] prevent ARMCC from hoisting the ordinary buffer load ahead of the ordinary count store. Candidate 2 tests whether the simpler interface is sufficient; candidate 3 addresses that ordering separately.

### Compiler behavior targeted

The intended access sequence is:

```cpp
const int newSize = mSize + 1; // ordinary read: eligible for reuse
ordered->mSize = newSize; // volatile store
LiveActor** buffer = ordered->mBuffer; // subsequent volatile pointer load
```

The first read stays nonvolatile so that ARMCC can potentially reuse the membership loop's cached count—the target's ip—rather than being required to perform another count read. The next two accesses establish the count-store-before-buffer-load constraint. Volatile-qualified access paths affect observable access requirements; they do not prescribe physical registers or the scheduling of unrelated arithmetic. The exact ARMCC lowering remains an untested hypothesis.

The local buffer is an ordinary LiveActor**. This does not make the actor slots volatile. Likewise, newSize is an ordinary local, so the returned element reference can use it without rereading the count after the store.

This form specifically targets the pair:

```
str r0, [r5, #4]
ldr r3, [r5, #8]
```

and, indirectly, the opportunity to overwrite r0 with the offset afterward. Both appear in that order in the target.

Main risks: ARMCC may stop reusing the membership count and introduce another load; it may retain the right memory order but put mvn r2, #3 earlier; or it may choose different registers despite the improved lifetime. This is a compiler-ordering experiment, not a concurrency protocol or a claim about the original source's use of volatile.

## What to look for if all three miss

First compare against the actual old form-2 disassembly, not the historical 74-byte listing. Preserve a per-instruction diff as well as the total differing-byte count. The important distinctions are:

| Observation | Interpretation |
|---|---|
| Candidate 1 improves 0x252B64–0x252BA8, while candidate 2 improves 0x252BD8–0x252BEC | The cancellation boundary and append interface likely address separate defects. Their combination is then evidence-led rather than speculative. |
| Candidate 1 emits exactly the old form-2 bytes | The helper boundary was erased too early to change the relevant optimization decisions. Repeating helper-name or declaration-order variations is unlikely to help. |
| Slot address is still formed after the actor comparison | The representation-copy address-preservation hypothesis did not survive. This is a structural failure, not merely wrong register coloring. |
| Append order becomes correct in candidate 3, but another count load appears | The volatile pair addressed scheduling, while reuse of the membership count was lost. Distinguish that extra load from a register-only miss. |
| Loads/stores and branches are otherwise correct, but queue remains in ip rather than r5 | Inspect interference with the opposing buffer and replacement value. r5 is an allocation consequence here, not evidence of a missing helper call. |

For the opposing count, verify the four separate points: nonmatch reload at 0x252B74, match-bound reload at 0x252B7C, post-replacement reload at 0x252B94, and decrement store at 0x252B9C. The stored decrement result must feed the latch comparison without another reload. For append, distinguish wrong memory order, wrong arithmetic, and right operations with wrong registers; those are different failures.

Finally, reject structural regressions before interpreting small byte-score changes: surviving memcpy or helper calls, spills, additional saved registers, unrolled membership search, a literal pool, or any extent other than the full 220-byte interval ending at 0x00252BF8. The next decision should be based on which of these three controlled changes moves the actual residual instructions—not on equal size alone.
