## 3. Compiler behavior targeted by the changes

The primary experiment: change copy lowering, not object layout.

| Change | Compiler behavior being targeted |
|---|---|
| Replace three assignments in the reader with *out = value | Introduce a C++ inline-call boundary specifically around the final copy, while retaining the existing wrapper-to-reader boundary. |
| Define the assignment operator explicitly | Give that inline operation a scalar x, y, z body rather than relying on compiler-generated aggregate-copy lowering. This does not prohibit subsequent merging, but makes the intended scalar operation explicit. |
| Return Vector3& from the operator, with its result discarded | Test whether the inliner and allocator give the copy a different return-register/live-range structure before the enclosing Boolean return is materialized. |
| Leave the wrapper, guards, constructor, and symbol references alone | Minimize disturbance to the prefix and literal pool that already match in form 1. |

The critical qualification: a user-defined assignment operator does not require ARMCC to use r0. Its unused reference result may disappear early, and the three assignments may become exactly the same compiler representation as before. If that happens, this candidate will probably reproduce the existing 22-byte mismatch.

The rationale is therefore an inlining/register-allocation hypothesis, not a claim that C++ assignment semantics enforce instruction order.

### Register allocation required by the target

| Register | Required role |
|---|---|
| r4 | Preserve the caller's output pointer across all four calls. |
| r5 | Preserve info->mPlacementInfo, loaded once from [r1]. |
| r6 | Hold the temporary vector's base address, introduced before the y lookup and reused for the z address. |
| r7 | Hold zero for the common failure return, surviving subsequent calls. |

The temporary occupies [sp], [sp,#4], and [sp,#8]. Saving five registers consumes 20 bytes; the additional 12-byte local allocation makes the total stack movement 32 bytes.

Several details are worth preserving rather than "cleaning up":

- The placement pointer is loaded, not formed. ldr r5, [r1] agrees with the actual pointer member at offset zero. Embedding a ByamlIter into ActorInitInfo, copying one into a local, or changing the placement accessor into a value-returning operation would attack a layout that already agrees with the target.
- The validity test remains a call. Although the committed provider implements isValid() as a test of mData, the target requires the bl to 0x276AA0. The candidate does not move that implementation into the header or substitute a direct field test.
- The temporary remains uninitialized. The existing empty Vector3 constructor is appropriate. Initializing it to zero or one would add operations for which the target has no evidence. The three successful lookups establish its components before the copy.
- The peculiar r6 lifetime is retained as an output requirement, not expressed as a register variable. The target first passes sp directly for x, then creates r6 = sp before y, and finally uses r6 + 8 for z. Adding an explicit source-level pointer or register declaration would not establish that precise allocation and could disturb the correct prefix.

### Why the mismatch is more than "move return true later"

The required success tail is:

```
0024ECF0 ldr r0, [sp]
0024ECF4 str r0, [r4]
0024ECF8 ldr r0, [sp, #4]
0024ECFC str r0, [r4, #4]
0024ED00 ldr r0, [sp, #8]
0024ED04 str r0, [r4, #8]
0024ED08 add sp, sp, #0xc
0024ED0C mov r0, #1
0024ED10 pop {r4, r5, r6, r7, pc}
```

The best form instead starts that tail with:

```
0024ECF0 ldr r1, [sp]
0024ECF4 mov r0, #1
0024ECF8 str r1, [r4]
```

It keeps using r1 for the remaining copies. These are the packet's observed differences, not predicted output from the proposed source.

Those differences are coupled: once r0 holds the final Boolean across the copies, the copy words need another register. Conversely, if the copy words occupy r0, the final mov r0,#1 cannot leave its result live across later loads into that same register.

That is why I would target the inline copy's live ranges rather than simply move a Boolean assignment around in the C++ text. The existing source already puts return true after all three stores; that textual ordering did not prevent the observed early materialization.

The desired allocation still does not fully determine the epilogue. Even after obtaining r0 copies, ARMCC must retain:

```
add sp, sp, #0xc
mov r0, #1
```

rather than reversing those independent instructions. That final ordering remains a separate matching risk.

The failure tail must also remain:

```
0024ED14 add sp, sp, #0xc
0024ED18 mov r0, r7
0024ED1C pop {r4, r5, r6, r7, pc}
```

An equivalent mov r0,#0, a shared epilogue, or removal of r7 would still fail exact matching.

I am not recommending a scheduling barrier as a substitute for this experiment. ARM's documentation describes sequence-point restrictions for __schedule_barrier; it does not provide a contract selecting a particular copy register or epilogue order. (Source cited: Arm Support.)
