## Platform

## Users

The owner runs a local browser demo from their own approved EU game dump. Contributors inspect source and rerunnable evidence. These users and the local operating context come from project/BRIEF.md and the owner's port instructions.

## Product Purpose

Demonstrate the actual Super Mario 3D Land port in a browser while matching proceeds independently. The browser demo has priority, followed by complete byte-exact reconstruction. Milestone M3 requires World 1-1 to the goal under differential replay, not a screenshot or successful build alone.

## Operating Context

The matching ARMCC build stays authoritative. The port uses static ARM-to-C translations with an address-based exact-source replacement interface. The priority conversion source adapter is verified; complete rank-O adapter coverage remains open. Azahar, recorded inputs and unchanged initial user state provide the differential oracle. Only the integrator moves main, ranks and ledger.

## Capabilities and Constraints

Actual finite Node wasm first-swap parity and local Chrome browser startup/frame parity are verified. The browser exports the first GPU swap and presentation 60 with exact raw events/ticks, PICA commands, framebuffer bytes and both displayed canvas buffers. File rejection and stop/retry recovery pass. Continuous browser controls/audio and World 1-1 remain unverified. Game data, generated guest code/binaries, input snapshots and game screenshots stay local and ignored. No deployment, upstream posting or external accounts are in scope.

The optional recorded-menu profile also matches all delivered movie HID, raw HLE PCM/events and rendered outputs against Azahar. After orderly completion it offers explicit playback of the actual browser-generated clip. AudioBuffer conversion, an equal-rate offline graph, a separate channel-distinct control and real WebAudio play/stop/natural end pass. This establishes completed-clip output; synchronized continuous sound, recognizable speaker content and device fidelity remain unverified.

The optional live A-button profile now records actual browser input through normal HID. A newly generated movie reproduces every delivered input/audio/GPU/tick/PICA/framebuffer/RGBA byte in stock Azahar. The held-state setter and CPU-sampled progress use atomics; accepting a request earns no delivery claim. Hold A operates only during the finite capture, with pointer/keyboard/focus release handling. Without the optional frame-output profile, screens and completed sound arrive after shutdown.

The optional frame-output profile shows bounded samples of completed software screens during execution. The CPU copies paired screens into owned slots; the worker copies ordinary buffers and releases each lease before sending them. Busy slots skip frames without delaying the guest. The final selected presentation remains a separate completion view. Per-frame source identity, canvas pixels, producer drop/duplicate counters, fresh stock image checkpoints and full final movie replay have separate acceptance checks. Sustained frame rate, synchronized continuous sound, mobile device performance and World 1-1 remain open.

The local page must be nontechnical and show real output. It must distinguish startup, running, completion and failure without claiming unobserved gameplay. Owner files remain read-only inputs. Screens and replay evidence have separate acceptance checks.

## Implementation Assumptions

Routine implementation choice: static HTML/CSS and native ES module JavaScript, alongside the existing Emscripten/C++ runtime. This adds no frontend framework or package dependency. The initial surface is a bounded preview with an owned-file control and two real screens. No claim is made that the owner chose a visual direction or standing build workflow.

## Product Principles

Observed execution earns a claim. Preserve original inputs and the oracle. Keep game data local. Let actual game output lead the page. Record remaining gaps precisely.
